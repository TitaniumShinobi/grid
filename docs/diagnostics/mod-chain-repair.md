# Evidence-bound mod-chain repair

Grid repairs an installed mod chain only from a sealed, sufficient baseline. The workflow is dependency-aware and deterministic:

```text
verify baseline -> inspect exact inputs -> quarantine artifacts -> materialize proposal
                -> authorize transaction -> stage -> commit -> verify or recover
```

Baseline reuse requires a valid case seal, compatible capability bindings, matching installation and active-profile identities, complete required gates, and unchanged protected hashes. Missing or ambiguous Grid-owned installation context is `InstallationContextUnresolved` with recovery disposition `ConfigurationRequired`; it is not an external dependency. Changed protected state is `BaselineStale`, and missing or stale partitions are refreshed without a global profile scan. `ExternalDependencyRequired` is reserved for an exact evidence-identified artifact proven unavailable from every authorized source. Conversation text and guessed paths are not substitutes for connected evidence.

## Provenance and acquisition boundary

MO2 `meta.ini` supplies claims, not proof. Baseline records preserve the parsed version fields, provider game/mod identifiers, categories, repository, timestamps and status, notes/comments, raw bounded values, and the exact `installationFile` claim. Only graph-relevant providers are eligible for source-archive observation. Grid checks exactly `<downloads>/<installationFile>` and its exact `.meta` sidecar as immediate children, without enumerating or recursively searching Downloads. Each observation records state, size, timestamp and a streaming SHA-256 when readable; the filename does not establish artifact identity or prove that the archive produced the installed directory.

Existing verified archives take precedence. New acquisition is restricted to evidence-derived artifacts from allowlisted HTTPS providers and lands in immutable quarantine. The resumable acquisition record binds provider game/mod/file/version identity, exact observed bytes, redirects, validators, size, SHA-256, and sealed evidence IDs. Partial transfers resume only under an unchanged ETag or Last-Modified validator; the default evidence-derived ceiling is 1 GiB. Credentials are accepted only through an opaque OS-protected handle and are redacted from receipts. When authentication or a browser session is required, Grid emits one managed-inbox `PendingUserAcquisition` action instead of calling the artifact unavailable. `ExactArtifactUnavailable` is permitted only after provider identity is verified and every authorized source has a terminal observation. A rejected artifact remains quarantined and is never made visible to MO2.

Inspection derives its component closure from provider seeds in the sealed InvestigationPlan plus the sealed mod, plugin/master, provenance, archive, and virtual-provider inventories. Caller-supplied component paths cannot expand that closure. Archive inspection is bounded and non-executing. It rejects traversal, reparse/device entries, alternate data streams, normalized or case-colliding paths, excessive depth/count/expansion/compression ratios, corruption, encryption and unsupported installer logic. Formats such as 7z that do not expose trustworthy per-member compressed sizes are checked against the bounded whole-archive expansion ratio instead of fabricating per-member ratios. FOMOD decisions come only from parsed `info.xml` and `ModuleConfig.xml`; repeated group labels are qualified by install-step identity, while every choice remains explicit in the selected option vector. Verified artifact identity, compatibility evidence, the source-to-destination map, preconditions, postconditions, and protected profile decisions are part of the immutable repair specification. Unsupported or contradictory installer logic leaves the baseline insufficient rather than selecting an option.

Archive-candidate classification is separate from archive integrity and installation. Given exact current plugin digests, version evidence, and the complete current dependent-plugin set, Grid classifies a candidate as `ExactRestoration`, `CompleteUpdateCandidate`, `CompleteRollbackCandidate`, `CompleteAlternativeCandidate`, `IncompleteCandidate`, or `Rejected`. During a bounded baseline, Grid includes the archive declared by current MO2 mod metadata plus immediate Downloads-folder archive/sidecar pairs whose redacted sidecar identity exactly matches the same Nexus repository, game, and mod ID; unrelated downloads are excluded. Explicit candidate member paths are used when supplied; otherwise only a unique plugin leaf and an exact-stem or sole BSA/BA2 payload are accepted. When a FOMOD contains multiple same-named BSA/BA2 variants, an exact installed archive SHA-256 may identify the one already selected; filename or resolution-label guesses may not. A differing candidate plugin and asset archive are an indivisible pair: mixing the candidate archive with the installed plugin is explicitly rejected. Bundled dependent plugins are classified independently as already matching, replacement-required, or not bundled. Every non-exact candidate remains `RequiresDependentCompatibilityEvidence`; a valid FOMOD that still needs choices additionally remains `SelectionRequired`. Baseline 2.6 seals these assessments beside archive-content evidence, carries them through post-collection finalization, and exposes every matching downloaded version in Repair Review. An exact restoration still needs packaged payload verification, and a version-changing candidate cannot become repair-ready from file coverage alone. These states are evidence and never constitute an update recommendation, installer selection, or mutation authorization.

For a FOMOD-backed installed provider, Grid may reconstruct the prior selection only from the complete sealed provider-file inventory and exact content hashes. Every option mapping is compared with the files currently supplied by the exact provider lineage. A wholly absent optional mapping can prove an explicit empty `SelectAny` choice; an exact installed BSA/BA2 digest can distinguish otherwise shared resolution variants. Partial matches, locally modified files, missing inventory coverage, and contradictory mappings remain unresolved. A recovery-source refresh carries the complete sealed file ledger forward from the nearest non-refresh baseline so this reconciliation does not silently degrade to plugin-and-archive-only evidence. Native child-process output is accepted only after its JSON contract and deterministic evidence identifier validate; a missing PowerShell process exit-code projection cannot discard otherwise valid evidence.

## Proposal and transaction

The repair specification binds the baseline digest, before-state hashes and every exact source, destination, installer selection, commit strategy, precondition, postcondition, exclusion and rollback location. Inspection and proposal materialization are inert. Active-tree mutation requires a separate authorization bound to that exact specification; any context, evidence, target or hash change makes it stale.

Repair never occurs in place. Complete replacement trees are staged outside the active mod directory and verified first. Original directories are copied or renamed into verified rollback storage before promotion, and source archives remain immutable. Grid preserves directory names, MO2 priorities, plugin ordering, comments, encodings and unrelated profile rows unless an exact profile edit is independently proved and enumerated.

For an asset-only diagnosis, the specification must declare `recordPatch.required=false`, `recordPatch.status=NotApplicable`, and an empty record list. Grid chooses an owning-mod replacement only when the verified archive and deterministic installer mapping reconstruct the complete expected tree; otherwise an evidence-bound overlay is allowed only when the proved payload is independently safe. No ESP is generated as a side effect of asset restoration.

The executor writes and flushes a hash-chained journal before the first mutation and after each primitive. It uses the strongest proven strategy for each target—side-by-side activation, same-volume rename, a validated root swap, or verified copy/flush/switch—and calls the overall operation a recoverable journaled transaction unless one atomic commit boundary is actually established. A failure or restart resumes or rolls back in reverse dependency order. Rollback is verified only when the prior trees and protected hashes are restored exactly; failed replacement content is quarantined rather than destroyed.

Static success and runtime certification are separate receipts. Certification resolves only the exact sealed baseline -> diagnosis -> repair lineage supplied by the active plan. A pending managed acquisition produces `PreconditionsNotMet`, `RuntimeValidation=NotStarted`, and `ReadyToPlay=NotEvaluated`; it never launches Skyrim against the unrepaired state. Eligibility additionally requires a committed repair receipt, passing static and virtual-winner receipts, protected-state equality, a valid journal digest, and a non-empty verified rollback manifest.

After eligibility, runtime certification evaluates eight independent gates. The seven prelaunch gates are installation, compatibility, asset, record, plugin, profile, and rollback integrity; runtime integrity is never inferred from them. The evaluator binds a versioned allowlisted recipe to the exact lineage, verified rollback receipt, disposable-profile plan, empty isolated save root, typed MO2 `-p` route, unambiguous owned-process evidence, bounded screenshots/logs, and a deterministic oracle result covering every required claim exactly once. Missing route or oracle evidence returns `NeedsRuntimeVerification`; screenshots alone never set `ReadyToPlay=true`.

## Result dimensions

The audit records independent dimensions instead of collapsing uncertainty:

- lifecycle: `Planned`, `Running`, `Completed`, `Failed`, `Cancelled`;
- repair outcome: `NotAttempted`, `NoChangeRequired`, `Applied`, `NotApplied`, `Indeterminate`;
- mutation: `NotStarted`, `Staged`, `CommitInProgress`, `Committed`, `PartiallyCommitted`;
- rollback: `NotRequired`, `Available`, `InProgress`, `Verified`, `Failed`, `Indeterminate`;
- recovery: `None`, `AutomaticRetryAvailable`, `ResumeAvailable`, `RollbackAvailable`, `ConfigurationRequired`, `ExternalDependencyRequired`, `ManualRecoveryRequired`.

A sufficient inspection with no necessary operations may materialize a zero-operation specification and return `InputsVerified`. Such a specification requires no authorization and cannot be passed to the mutation executor.

When the operator input supplies a `repairCaseId`, proposal materialization also seals the inspection and inert specification as an append-only repair-planning case in the configured Grid case store. Reusing that ID is idempotent only when the sealed specification bytes match; a different specification is a collision and is refused.

`InputsVerified` means no mutation was needed and all readiness postconditions passed. `InputsRepairedAndVerified` requires a committed replacement plus verified physical files, masters, versions, virtual winners and profile invariants. `RepairRolledBack` requires exact prior hashes. `ManualRecoveryRequired` is used only when journal evidence proves automated recovery cannot safely finish.

Idempotency binds the repair-specification digest, baseline-manifest digest and before-state hashes. Replaying a terminal verified transaction returns its existing receipt. Receipts and rollback packages remain retained until an explicit exact deletion operation.

This workflow does not construct a conflict patch, edit saves, launch the game, validate gameplay, sort with LOOT, disable an overhaul as a fix, refresh unrelated mods or reinstall the profile.

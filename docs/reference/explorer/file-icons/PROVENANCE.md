Upstream package: `material-icon-theme` 5.33.1, publisher PKief / Material Extensions, package description “Material Design Icons for Visual Studio Code.” CODE declares `^5.33.1` in `package.json`; `package-lock.json` resolves the 5.33.1 npm tarball; the installed package is 5.33.1. This is **Material Icon Theme**, not VS Code built-in Seti, `vscode-icons`, or CODE-owned artwork.

Primary CODE source: `src/CodeWorkspaceScreen.tsx` imports `generateManifest` from the package, calls `generateManifest({ activeIconPack: 'react' })`, and eagerly maps `node_modules/material-icon-theme/icons/*.svg` to Vite asset URLs. This is a local installed npm package at build time, not a dynamic icon CDN. The generated `dist` may contain copied/hashed build artifacts; the authoritative source is the npm dependency, not a CODE-maintained icon set.

For each **file** row: `renderTree` passes `relativePath` to `FileTreeThumbnail`; it lowercases the path and basename; applies CODE's overrides for `npm-shrinkwrap.json`, `package-lock.json`, `package.json`, and `readme.md`; then checks package `fileNames` by basename and full relative path; then checks `fileExtensions` in descending extension-key length (important for compound extensions); then checks `languageIds` using CODE's narrow `languageForPath`; then falls back to package default `file`. The icon ID resolves through `manifest.iconDefinitions[id].iconPath` to an SVG filename and then to the Vite asset URL. For certain image/media extensions, an asynchronously loaded data URL replaces the SVG with a thumbnail; failure leaves the Material icon.

For each **folder** row: CODE renders `▾` or `▸` according to expansion state and the folder name. It does not call `materialIconIdForFile`, does not render `manifest.folderNames`, and does not use folder SVGs. The upstream manifest does contain generic `folder` / `folder-open`, root folder variants, and special-folder mappings (e.g. `src` → `folder-src`, `assets` → `folder-resource`) plus expanded variants, but they are **not CODE Explorer behavior** and are intentionally excluded. GRID may independently opt into upstream folder icons later, but that would extend rather than reproduce CODE.

CODE always reads base `fileNames`/`fileExtensions`/`languageIds` and base icon definitions. It does not branch to the manifest's `light` or `highContrast` file maps for the Explorer, despite such variants existing upstream. Its UI theme may change surrounding CSS, but file-icon selection does not change with it.

The handoff generation selected the exact reachable file-icon IDs from CODE's resolver and copied their referenced SVG filenames from `node_modules/material-icon-theme/icons`. `source/code-file-icon-map.json` is a snapshot of the relevant 5.33.1 manifest fields, not a runtime dependency on npm. `CodeFileIconResolver.cs` ports the selection algorithm for .NET; it does not copy upstream executable JavaScript. 580 distinct SVG assets were copied; no asset was missing at generation time.
